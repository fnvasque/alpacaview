Objetivo V0.3b:
Crear un outcome evaluator que mida qué habría pasado después de cada señal generada.

El sistema debe:
1. Buscar señales generadas por el forward tester en forward_test_runs.
2. Considerar solo filas con client_signal_id no nulo y price, stop_loss, take_profit presentes.
3. Evaluar señales con status:
   - signal_candidate
   - risk_approved
   - risk_rejected
   - duplicate_signal
4. Excluir:
   - no_signal
   - skipped_market_closed
   - insufficient_data
   - error
5. Por defecto excluir is_dry_run=true, salvo que se pase flag --include-dry-run.
6. Descargar velas posteriores usando yfinance.
7. Evaluar para señales BUY:
   - si una vela posterior tiene high >= take_profit → take_profit_hit
   - si una vela posterior tiene low <= stop_loss → stop_loss_hit
   - si la misma vela tiene high >= take_profit y low <= stop_loss → ambiguous_same_bar
   - si no ocurre ninguno después de OUTCOME_LOOKAHEAD_BARS → timeout
   - si todavía no hay suficientes velas futuras → pending
8. No evaluar la misma vela de entrada; empezar desde la vela siguiente a bar_time.
9. Crear tabla signal_outcomes.
10. La evaluación debe ser idempotente por client_signal_id.
11. Si ya existe outcome terminal para un client_signal_id, no duplicar.
12. Permitir re-evaluar outcomes pending.
13. Calcular:
   - outcome
   - outcome_bar_time_utc
   - bars_to_outcome
   - pnl_r
   - pnl_pct
   - max_favorable_excursion
   - max_adverse_excursion
14. Agregar CLI:
   python -m src.outcome_evaluator.cli --once
15. Flags:
   - --once
   - --tickers SPY,QQQ,AAPL,MSFT,NVDA
   - --timeframe 15m
   - --period 5d
   - --lookahead-bars 26
   - --include-dry-run
   - --client-signal-id
   - --dry-run
16. Si --dry-run, imprimir evaluación pero no escribir cambios.
17. Si no --dry-run, escribir o actualizar signal_outcomes.
18. No modificar /webhook/signal.
19. No agregar Alpaca.
20. No crear órdenes.
21. Agregar tests unitarios e integración.
22. Agregar documentación en docs/validation/v0.3b-validation.md.

Decisiones recomendadas:
- Usar una tabla nueva signal_outcomes.
- Usar forward_test_runs como fuente principal.
- Mantener outcomes ambiguos como ambiguous_same_bar, no asumir victoria ni pérdida.
- Default OUTCOME_LOOKAHEAD_BARS=26, equivalente aproximado a una sesión de mercado de 15m.
- Evaluar risk_rejected también, porque sirve para medir oportunidades bloqueadas por el Risk Engine.

## Domain Concept Identification

### Existing Concepts (from codebase)

- **ForwardTestRun** (`app/models/forward_test_run.py`): The source table for outcome evaluation. Contains `client_signal_id`, `price`, `stop_loss`, `take_profit` (4dp strings, nullable), `bar_time` (nullable UTC DateTime), `status` (string), `is_dry_run` (bool), `ticker`, `timeframe`, `period`. No unique constraint on `client_signal_id` — the same signal can appear in multiple rows (e.g., evaluated once in dry-run and once in send mode). Columns `run_id` and `ticker` are indexed.

- **RunStatus values** (defined in `src/forward_testing/runner.py`): The status taxonomy includes `signal_candidate`, `risk_approved`, `risk_rejected`, `duplicate_signal`, `no_signal`, `skipped_market_closed`, `insufficient_data`, `error`, `signal_sent`. The first four are the "evaluable" statuses — they have a real signal with price/sl/tp.

- **`client_signal_id` format** (generated by `src/signal_generator/signal_builder.py`): `python_atr_generator:0.2b.0:{TICKER}:{TIMEFRAME}:{bar_time_Z}:buy` — fully deterministic from the signal bar. Guarantees that any two rows with the same `client_signal_id` describe identical price/sl/tp/bar_time parameters.

- **`fetch_ohlcv(ticker, period, timeframe)`** (`src/signal_generator/data_fetcher.py`): The existing yfinance wrapper. Returns a pandas DataFrame indexed by UTC-aware DatetimeIndex with columns `Open`, `High`, `Low`, `Close`. Handles multi-index flattening. Raises `DataFetchError` on failure. This is the correct reuse point for downloading outcome bars — no new yfinance integration needed.

- **`DataFetchError`** (`src/signal_generator/data_fetcher.py`): The standard exception for fetch failures. Outcome evaluator must catch and handle this.

- **`Base` / `init_db`** (`app/database.py`): Declarative base shared by all ORM models. The outcome evaluator's new `SignalOutcome` model must inherit `Base` to participate in `Base.metadata.create_all()`.

- **`ForwardTestingSettings` pattern** (`src/forward_testing/config.py`): Blueprint for the new `OutcomeEvaluatorSettings` — `BaseSettings` + `extra="ignore"` + comma-separated ticker validator + `model_validator` secret fallback.

- **CLI architecture pattern** (`src/forward_testing/cli.py`): Blueprint for the outcome evaluator CLI — `click.command()`, `_init_db(db_url)` returning `(engine, Session)`, per-item error isolation, `has_error` flag, `sys.exit(1 if has_error else 0)`.

### New Concepts Required

- **SignalOutcome** (`app/models/signal_outcome.py`): New ORM model / SQLite table `signal_outcomes`. Persists the evaluated outcome for one `client_signal_id`. Has a unique constraint on `client_signal_id` — one outcome row per signal, regardless of how many `forward_test_runs` rows reference it. Stores outcome type, timing, PnL metrics, and excursion metrics. Can be upserted on re-evaluation of `pending` outcomes.

- **OutcomeStatus** (enum, `src/outcome_evaluator/evaluator.py`): `take_profit_hit`, `stop_loss_hit`, `ambiguous_same_bar`, `timeout`, `pending`. The first four are **terminal** — once written, never updated. `pending` is **non-terminal** — re-evaluated each run until it resolves.

- **EvaluationResult** (dataclass, `src/outcome_evaluator/evaluator.py`): Ephemeral result of evaluating one signal against OHLCV data. Carries `client_signal_id`, `outcome` (OutcomeStatus), `outcome_bar_time_utc`, `bars_to_outcome`, `pnl_r`, `pnl_pct`, `max_favorable_excursion`, `max_adverse_excursion`, `error_message`. Never persisted directly — CLI maps it to `SignalOutcome`.

- **`evaluate_signal()`** (pure function, `src/outcome_evaluator/evaluator.py`): Takes a signal's parameters (`ticker`, `timeframe`, `price`, `stop_loss`, `take_profit`, `bar_time`) plus OHLCV DataFrame and `lookahead_bars`, returns `EvaluationResult`. No DB, no network, no click. Fully deterministic and unit-testable via injected mock DataFrames. Contains the core outcome logic: bar filtering, high/low comparison, MFE/MAE accumulation.

- **OutcomeEvaluatorSettings** (`src/outcome_evaluator/config.py`): pydantic-settings for the evaluator. Fields: `OUTCOME_EVALUATOR_ENABLED`, `OUTCOME_EVALUATOR_DB_URL`, `OUTCOME_EVALUATOR_TICKERS`, `OUTCOME_EVALUATOR_TIMEFRAME`, `OUTCOME_EVALUATOR_PERIOD`, `OUTCOME_LOOKAHEAD_BARS`, plus shared `EMA_LENGTH`, `ATR_LENGTH` if needed.

- **`OutcomeEvaluatorCLI`** (`src/outcome_evaluator/cli.py`): click CLI that owns DB init, signal sourcing from `forward_test_runs`, the per-signal evaluation loop, and DB upsert/skip logic. Mirrors `src/forward_testing/cli.py` architecture.

### Key Business Rules

- **Idempotency by `client_signal_id`**: `signal_outcomes` has a unique constraint on `client_signal_id`. If a terminal outcome already exists, skip silently. If `pending` exists, re-evaluate and update in place.

- **Entry bar exclusion**: Evaluation begins strictly from the bar immediately after `bar_time`. The entry bar itself is never scanned for outcome conditions.

- **Terminal outcomes are immutable**: `take_profit_hit`, `stop_loss_hit`, `ambiguous_same_bar`, `timeout` are final. They cannot be downgraded to `pending` or changed to a different terminal outcome on re-evaluation.

- **`pending` is mutable**: A `pending` outcome must be re-evaluated on every run until it resolves to a terminal outcome.

- **Dry-run exclusion is the default**: `is_dry_run=true` rows in `forward_test_runs` are excluded unless `--include-dry-run` is explicitly passed. When included, a `signal_candidate` from a dry-run is evaluated identically to a `risk_approved` from a live run — because the signal parameters are the same.

- **Evaluation source uniqueness**: The same `client_signal_id` can have multiple `forward_test_runs` rows. Signal parameters (price, sl, tp, bar_time) are deterministic from the signal ID — any qualifying row can be used as the source. One `signal_outcomes` row is written per unique `client_signal_id`.

- **`ambiguous_same_bar` has no PnL**: If `high >= take_profit` and `low <= stop_loss` within the same bar, the outcome is genuinely unknown. `pnl_r` and `pnl_pct` must be `None` — no assumption about which level was hit first.

- **No server or Alpaca interaction**: The evaluator reads from `forward_test_runs`, downloads yfinance data, and writes to `signal_outcomes`. It does not call `/webhook/signal`, does not query the Risk Engine, and has no Alpaca imports.

## Strategic Approach

### Solution Direction

- **Standalone `src/outcome_evaluator/` package**: Mirrors `src/forward_testing/` structure. Invoked as `python -m src.outcome_evaluator.cli --once`. Never modifies server-side components.

- **DB model in `app/models/`**: `SignalOutcome` inherits `Base`, ensuring automatic table creation via `Base.metadata.create_all()`. Registered in `app/models/__init__.py` following the existing pattern.

- **Pure evaluator function**: `evaluate_signal()` receives all inputs as arguments (signal params + pre-fetched DataFrame + lookahead_bars). No I/O. Returns `EvaluationResult`. The CLI layer owns fetching data from yfinance and from the DB.

- **Reuse `fetch_ohlcv`**: No new yfinance integration. The existing `fetch_ohlcv(ticker, period, timeframe)` returns a DataFrame whose index includes all bars within `period` days of now. The evaluator filters this DataFrame to bars strictly after `bar_time`.

- **Data flow**: DB query (`forward_test_runs`) → group by `client_signal_id` → for each unique signal: check idempotency → fetch OHLCV → call `evaluate_signal()` → upsert `SignalOutcome` or skip → echo result.

- **Per-signal error isolation**: `DataFetchError` or evaluation exception for one signal does not stop the batch. Logged, `has_error = True`, loop continues.

### Key Design Decisions

- **Decision 1 — `--period` semantics in the outcome evaluator**: The `period` parameter (e.g. `5d`) controls how much historical OHLCV data is downloaded via yfinance — identical semantics to `forward_testing`. The evaluator then filters the returned DataFrame to only bars with index strictly greater than `bar_time`. For `lookahead_bars=26` (≈1 day of 15m), `period=5d` covers signals up to ~4 days old. For very old signals, the user should pass a larger `--period`. → **Recommendation: identical semantics to forward_testing, default `5d`.**

- **Decision 2 — Source row selection for duplicate `client_signal_id` rows**: Multiple `forward_test_runs` rows can share the same `client_signal_id`. When determining which row to use as the signal source, pick the first row (by `created_at_utc`) that has `price`, `stop_loss`, `take_profit`, and `bar_time` non-null. The CLI should deduplicate by `client_signal_id` before the evaluation loop — one fetch + one evaluation per unique ID. → **Recommendation: deduplicate in the query, first qualifying row wins.**

- **Decision 3 — `pnl_r` and `pnl_pct` calculation**:
  - `take_profit_hit`: `pnl_r = risk_reward` (read from the signal row, e.g. 2.0), `pnl_pct = (take_profit - price) / price * 100`
  - `stop_loss_hit`: `pnl_r = -1.0` (always -1R), `pnl_pct = (stop_loss - price) / price * 100`
  - `ambiguous_same_bar`: `pnl_r = None`, `pnl_pct = None`
  - `timeout` / `pending`: `pnl_r = None`, `pnl_pct = None`
  → **Recommendation: as above.**

- **Decision 4 — `outcome_bar_time_utc` for non-signal outcomes**:
  - Terminal outcomes: the timestamp of the bar where the outcome was detected.
  - `timeout`: the timestamp of the last evaluated bar (the bar at position `lookahead_bars` after entry). This records when the window closed.
  - `pending`: `None` — no end bar yet.
  → **Recommendation: as above.**

- **Decision 5 — MFE/MAE for `pending` outcomes**: Store the current maximum favorable / adverse excursion across all available bars so far. When the outcome later resolves, the updated values replace them. This provides partial insights during the evaluation window. MFE for BUY = max(high) over evaluated bars. MAE for BUY = min(low) over evaluated bars. Both stored as 4dp decimal strings (percent vs. price? → see ambiguity #5). → **Recommendation: store as 4dp price strings (not percent), same format as `price`/`stop_loss`/`take_profit`.**

- **Decision 6 — `bars_to_outcome` for `timeout` and `pending`**:
  - Terminal outcomes: count of bars from entry to outcome bar (min 1, since entry bar is excluded).
  - `timeout`: `lookahead_bars` — the full window was consumed.
  - `pending`: number of bars available after entry at evaluation time (represents current progress).
  → **Recommendation: as above.**

- **Decision 7 — `risk_reward` field availability**: The `forward_test_runs` table stores `risk_reward` as a 4dp string (e.g. `"2.0000"`). This is available directly for use in `pnl_r` calculation for `take_profit_hit`. The evaluator should read it from the source row rather than recomputing it. → **Recommendation: read `risk_reward` from `forward_test_runs` directly.**

### Alternatives Considered

- **Storing multiple outcome rows per signal**: Rejected — violates idempotency. One row per `client_signal_id` is the cleanest contract. Updates go to the same row.

- **Fetching OHLCV from a dedicated date range (start=bar_time, end=bar_time + N intervals)**: yfinance supports `start`/`end` params but this is less battle-tested in the existing codebase. The existing `fetch_ohlcv` uses `period` and is already tested. Stick with it. → Rejected in favor of reusing existing function.

- **Evaluating the same bar as entry**: Rejected by requirement. Entry is excluded to avoid the degenerate case where price, sl, and tp were all within the entry bar itself.

- **Storing `pnl_pct` as `pnl_r * risk_pct`**: Could compute pnl_pct as `pnl_r * (price - stop_loss) / price * 100`, which is cleaner. But direct calculation from `take_profit - price` and `stop_loss - price` is more transparent and self-documenting. → Rejected in favor of direct calculation.

## Risk & Gap Analysis

### Requirement Ambiguities

- **Ambiguity 1 — `period` in `evaluate_signal` vs. data availability for old signals**: If `bar_time` is 7 days ago and `period=5d`, yfinance returns only the last 5 days, which may not include `bar_time` at all. The evaluator would find zero bars after `bar_time` and incorrectly classify the outcome as `pending` instead of `timeout`. Mitigation: document clearly in the operator guide that `--period` must cover `bar_time + lookahead`. For standard use (signals < 3 days old), `period=5d` is sufficient.

- **Ambiguity 2 — How `bar_time` aligns with the yfinance DataFrame index**: yfinance returns bars with timestamp = bar open time in UTC (for most intervals). `bar_time` in `forward_test_runs` is the UTC start of the closed bar — this should align with yfinance's index. However, for intraday bars, yfinance sometimes returns timezone-aware or timezone-naive timestamps depending on the interval and pandas version. The filter `df.index > bar_time` must handle both aware and naive cases. The `compute_indicators` function in `src/signal_generator/indicators.py` already handles this; the outcome evaluator must apply the same defensive pattern.

- **Ambiguity 3 — `--tickers` vs. `--client-signal-id` interaction**: When `--client-signal-id` is passed, should `--tickers` be ignored? Or should the evaluator still validate that the signal's ticker matches the allowed list? Recommendation: when `--client-signal-id` is passed, bypass the ticker list entirely and evaluate only that specific signal.

- **Ambiguity 4 — Whether `risk_reward` can be `None` in `forward_test_runs`**: The `risk_reward` column in `forward_test_runs` is nullable — it's only populated when a signal was generated (crossover detected + payload built). For the evaluable statuses (`signal_candidate`, `risk_approved`, etc.), it should always be non-null. But the evaluator must guard against it and default to recomputing from `price`, `stop_loss`, `take_profit` if needed.

- **Ambiguity 5 — MFE/MAE format: price or percent?**: The requirement does not specify. Two options: (A) store as 4dp price strings matching the price columns, or (B) store as 6dp percent strings. Price is more informative for later analysis. → Recommendation: store as 4dp price strings.

- **Ambiguity 6 — What status to give a `pending` outcome that already wrote a `take_profit_hit` for a different row with the same client_signal_id**: Cannot happen because `client_signal_id` is unique in `signal_outcomes`. If a terminal row already exists, the re-evaluation is silently skipped.

### Edge Cases

- **All bars after `bar_time` are gap-filling or weekend gaps**: yfinance does not return weekend bars for equities. If `bar_time` is Friday 15:45 ET and we fetch `1d` of 15m data, the next bars will be Monday. The filter `df.index > bar_time` handles this correctly — gaps are invisible to the evaluator.

- **`bar_time` falls exactly on a bar boundary in the DataFrame**: The strict `>` comparison (`df.index > bar_time`) correctly excludes the entry bar even if it's present in the downloaded DataFrame.

- **Ticker delisted between signal generation and evaluation**: yfinance will either return an empty DataFrame or raise an exception. This is handled by `DataFetchError`, which marks the signal as an error (not stored in `signal_outcomes`) and continues the loop.

- **`ambiguous_same_bar` at bar index 1 (first bar after entry)**: Valid. The outcome is detected at the earliest possible bar. `bars_to_outcome = 1`, `outcome_bar_time_utc = timestamp of that bar`.

- **`lookahead_bars=0`**: Degenerate case — immediate `timeout` with no bars evaluated. `bars_to_outcome = 0`, MFE/MAE = None. Unlikely in practice but should not crash.

- **`--include-dry-run` and the same `client_signal_id` appearing in both dry-run and non-dry-run rows**: Since `client_signal_id` is deterministic from the bar, both rows represent the same signal. The source row selection logic (first qualifying row) handles this — the non-dry-run row would typically be `created_at_utc` earlier or equal. In practice this is fine because all rows with the same `client_signal_id` have identical price/sl/tp/bar_time.

- **`pending` outcome being re-evaluated after market data is no longer available**: If a `pending` signal is for a bar so old that yfinance no longer returns data for it, the outcome will remain `pending` indefinitely. This is an operational concern, not a code bug — document in validation guide.

- **`timeout` when `lookahead_bars` bars exist but none hit tp or sl**: Correct expected behavior. MFE = max high over all bars, MAE = min low over all bars, `bars_to_outcome = lookahead_bars`.

### Technical Risks

- **Risk 1 — Timezone mismatch between `bar_time` (stored as UTC) and yfinance DataFrame index**: The DataFrame index from yfinance for intraday bars may be timezone-naive or UTC-aware depending on version. If naive, direct comparison with timezone-aware `bar_time` will raise a `TypeError`. Mitigation: strip or normalize timezone before comparison, using the same defensive pattern as `compute_indicators` in `src/signal_generator/indicators.py` (lines 68–73).

- **Risk 2 — yfinance rate limiting for large ticker batches**: If the evaluator runs many tickers in rapid succession (e.g., 5 tickers × many signals), yfinance may throttle. Mitigation: one `fetch_ohlcv` call per ticker per run, not per signal. Group signals by ticker and fetch once.

- **Risk 3 — Unique constraint race condition on `signal_outcomes`**: If the CLI is invoked twice concurrently (e.g., two cron jobs overlapping), both could attempt to insert the same `client_signal_id`. SQLite serialises writes so this is unlikely in practice, but the upsert logic should be wrapped in a try/except for `IntegrityError`. Mitigation: idempotency check before insert (SELECT first, then INSERT or UPDATE).

- **Risk 4 — `risk_reward` from `forward_test_runs` being a slightly different Decimal from recomputed**: Due to floating point, `(take_profit - price) / (price - stop_loss)` recomputed as Decimal from stored 4dp strings may differ from the original by epsilon. For `pnl_r` on `take_profit_hit`, always use the stored `risk_reward` value from `forward_test_runs` directly — do not recompute.

- **Risk 5 — `--client-signal-id` with a signal not in the DB**: The evaluator must handle gracefully — emit a clear error message (not crash) and exit 1.
