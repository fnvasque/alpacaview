# V0.3 Forward Testing Runner — Operator Guide

## Overview

The Forward Testing Runner (`src/forward_testing/`) is a standalone Python CLI that runs the signal generator pipeline for a configurable list of tickers on each invocation and persists every evaluation result to the shared SQLite database — including no-signal outcomes. It is designed to replace manual TradingView monitoring during development and to build a persistent audit trail of signal opportunities.

It does not place orders. It does not connect to Alpaca. It only calls `POST /webhook/signal` on the local FastAPI server when a real signal is detected and `--send` is active.

---

## Quickstart

**1. Enable the feature**

Add to `.env`:

```
FORWARD_TESTING_ENABLED=true
FORWARD_TESTING_SECRET=change_me
```

**2. Run once (dry-run — no backend call)**

```bash
python -m src.forward_testing.cli --once --dry-run
```

**3. Run once and send to backend**

```bash
python -m src.forward_testing.cli --once --send
```

**4. Market-hours-only mode (skip outside 9:30–16:00 ET)**

```bash
python -m src.forward_testing.cli --once --send --market-hours-only
```

## CLI Flags Reference

| Flag | Type | Default | Behaviour |
|------|------|---------|-----------|
| `--once` | flag | `False` | No-op documentation flag. Accepted for cron/launchd readability. Does not change behaviour. |
| `--tickers` | string | settings | Comma-separated list. Overrides `FORWARD_TESTING_TICKERS`. Example: `--tickers SPY,NVDA` |
| `--timeframe` | string | settings | Bar interval. Overrides `FORWARD_TESTING_TIMEFRAME`. Example: `--timeframe 15m` |
| `--period` | string | settings | Lookback window. Overrides `FORWARD_TESTING_PERIOD`. Example: `--period 5d` |
| `--send` | flag | `False` | POST to `/webhook/signal` when a signal is detected. |
| `--dry-run` | flag | `False` | Evaluate signals without sending. Writes to DB with `is_dry_run=true`. This is the default when `--send` is not set. |
| `--market-hours-only` | flag | `False` | Exit 0 (and write `skipped_market_closed` rows) if outside US equity market hours. |

**Default behaviour**: If neither `--send` nor `--dry-run` is passed, the CLI behaves as dry-run (`effective_dry_run = dry_run or not send`). This prevents accidental backend calls.

## Operating Modes

| `--send` | `--dry-run` | `--market-hours-only` | Backend called? | DB written? | `is_dry_run` |
|----------|-------------|----------------------|-----------------|-------------|--------------|
| No | No | No | No | Yes | True |
| No | Yes | No | No | Yes | True |
| Yes | No | No | Yes (on signal) | Yes | False |
| Yes | No | Yes + closed | No | Yes (skipped) | False |
| No | No | Yes + open | No | Yes | True |

## RunStatus Reference

| Status | Meaning | Exit code contribution |
|--------|---------|----------------------|
| `no_signal` | No EMA crossover detected, or payload could not be built | 0 |
| `signal_candidate` | Dry-run: signal would have been sent | 0 |
| `signal_sent` | Signal sent but unexpected HTTP response (not 200/202/409) | **1** |
| `risk_approved` | Server returned 202 — risk engine approved | 0 |
| `risk_rejected` | Server returned 200 with `approved=False` | 0 |
| `duplicate_signal` | Server returned 409 with `reason_code=duplicate_signal` | 0 |
| `skipped_market_closed` | `--market-hours-only` active and market is closed | 0 |
| `insufficient_data` | `compute_indicators` returned None (not enough bars) | 0 |
| `error` | `DataFetchError`, network error, unexpected exception, or HTTP 4xx/5xx not handled above | **1** |

Exit code is **1** if at least one ticker resulted in `error` or `signal_sent`, or if at least one DB write failed. All other statuses produce exit code **0**.

## `forward_test_runs` Schema

| Column | Type | Nullable | Description |
|--------|------|----------|-------------|
| `id` | String (UUID4) | No | Primary key. Generated per row. |
| `run_id` | String (UUID4) | No | Shared across all tickers in one CLI invocation. Indexed. |
| `ticker` | String | No | Ticker symbol (e.g. `SPY`). Indexed. |
| `timeframe` | String | No | Bar interval (e.g. `15m`). |
| `period` | String | No | Lookback window (e.g. `5d`). |
| `status` | String | No | `RunStatus` string value (e.g. `no_signal`). |
| `is_dry_run` | Boolean | No | `True` if `--send` was not used. |
| `bar_time` | DateTime (UTC) | Yes | UTC start of the most recent closed bar. `None` for `no_signal`, `insufficient_data`, `skipped_market_closed`, `error`. |
| `client_signal_id` | String | Yes | Signal identifier. `None` when no signal generated. |
| `price` | String (4dp) | Yes | Entry price at signal time. |
| `stop_loss` | String (4dp) | Yes | Computed stop loss. |
| `take_profit` | String (4dp) | Yes | Computed take profit. |
| `risk_reward` | String (4dp) | Yes | Locally computed `(take_profit - price) / (price - stop_loss)`. |
| `backend_status_code` | Integer | Yes | HTTP status from `/webhook/signal`. `None` if not sent. |
| `backend_signal_id` | String | Yes | Server-assigned `signal_id` from response body. |
| `backend_approved` | Boolean | Yes | From response body `approved` field. |
| `backend_reason_code` | String | Yes | Risk engine reason code from response. |
| `backend_reason_detail` | String | Yes | Risk engine reason detail from response. |
| `error_message` | String | Yes | Populated only when `status=error`. Never contains secrets. |
| `created_at_utc` | DateTime (UTC) | No | Row creation timestamp. |

## `run_id` Semantics

Each CLI invocation generates one UUID4 `run_id` before the ticker loop begins. All `ForwardTestRun` rows from the same invocation share this `run_id`.

This enables batch-level queries:

```sql
SELECT * FROM forward_test_runs WHERE run_id = '<uuid>';
```

---

## Dry-Run Audit Trail

Dry-run runs produce full DB rows with `is_dry_run=true`. No HTTP call is made to the backend. No `Signal` or `RiskDecision` rows are created.

If a signal would have been sent in real mode, the row gets `status=signal_candidate`. If no signal was produced, the row gets `status=no_signal` or `status=insufficient_data`.

The same `client_signal_id` can appear multiple times in `forward_test_runs` — for example, when dry-run is called twice within the same 15-minute bar. There is no unique constraint on `client_signal_id`.

---

## Error Handling

Errors are isolated per ticker. If `SPY` fails to fetch, the runner records `status=error` for `SPY` and continues with `QQQ`, `AAPL`, etc.

At the end of the invocation, if any ticker resulted in `error` or `signal_sent`, the CLI exits with code **1**.

Non-error outcomes (`no_signal`, `risk_rejected`, `duplicate_signal`, `skipped_market_closed`, `signal_candidate`) never contribute to exit 1.

## Scheduling with cron

Run every 15 minutes during market hours (US Eastern):

```cron
*/15 9-16 * * 1-5 cd /path/to/alpacaview && /path/to/venv/bin/python -m src.forward_testing.cli --once --send --market-hours-only >> /tmp/fwd_test.log 2>&1
```

Example `~/Library/LaunchAgents/com.alpacaview.forwardtesting.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>com.alpacaview.forwardtesting</string>
    <key>ProgramArguments</key>
    <array>
        <string>/path/to/venv/bin/python</string>
        <string>-m</string>
        <string>src.forward_testing.cli</string>
        <string>--once</string>
        <string>--send</string>
        <string>--market-hours-only</string>
    </array>
    <key>WorkingDirectory</key>
    <string>/path/to/alpacaview</string>
    <key>StartInterval</key>
    <integer>900</integer>
    <key>StandardOutPath</key>
    <string>/tmp/fwd_test.log</string>
    <key>StandardErrorPath</key>
    <string>/tmp/fwd_test_err.log</string>
</dict>
</plist>
```

Load with: `launchctl load ~/Library/LaunchAgents/com.alpacaview.forwardtesting.plist`
